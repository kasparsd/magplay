# Architecture

## Decision

magplay stays a small Node service with a React browser client for one person on a trusted LAN, without accounts. [The roadmap](roadmap.md) owns priorities and completion status.

**Direction change (2026-10-17):** the code is reorganized into isolated packages and moved to strict TypeScript now, while the codebase is small (~5k lines) and the change is cheap. The server and packages are converted as scheduled work; client pages, tests and scripts convert when next touched ([roadmap](roadmap.md#what-to-do-next)). This replaces the earlier stance of deferring a TypeScript migration and factory refactors until a concrete bug required them. Reasons:

- Treating each area as if it were a standalone package exposed coupling that makes every fix and test harder: HTTP status codes thrown from the torrent/media/session logic, a global config imported for errors, configuration depending on indexer adapters, work done at import time, and modules that each hold several jobs (now resolved by the package boundaries below).
- The browser↔server API and the codec keys shared by the capability probe and the playback decision are only aligned by JSDoc and comments. Shared types make mismatches compile errors.
- Explicit factories with `close()` give tests and shutdown one owner per process, timer, port and directory, instead of module-level state.

Packages are internal npm workspaces. Publishing any of them is a later, optional step, not a goal. The server/package extraction and tightening review are delivered. Remaining client and tooling conversions happen on touch and are tracked in [the package boundaries and TypeScript plan](plans/package-boundaries-and-typescript.md).

## Package boundaries

Arrows show domain dependencies; nothing points back up, and no package imports an app. Server packages also consume the shared observability interfaces (see [logging](logging.md)).

```
apps/server ──► indexers ──────► release-info
     │      ──► torrent-engine ─► release-info
     │      ──► seekable-tar
     │      ──► playback ───────► api-contract (track, capability and session types; codec keys)
     │      ──► http-kit
     │      ──► observability ─► api-contract
     └──► api-contract ◄── apps/client
```

| Package | Responsibility | Takes in | Never knows about |
| --- | --- | --- | --- |
| `release-info` | Pure helpers: release badges, episode detection, file kinds, executable warning | Strings and file lists | Anything else |
| `indexers` | Torznab/Jackett/Prowlarr/BitMagnet adapters, normalized `Release`, parallel search with timeouts, deduplication, private link IDs | Source configs, `fetch` | Env vars, HTTP status codes |
| `torrent-engine` | `createTorrentEngine(options)`: add/get/status/recent torrents, metadata store, cache eviction, discovery/checking deadlines; files expose cancellable range reads | Cache dir, ports, DHT/LSD, trackers, limits | HTTP request/response objects |
| `seekable-tar` | PAX tar layout computed from file sizes, any byte range produced on demand | Sizes, a `read(range)` callback | Torrents, Node streams |
| `playback` | `probe(input)` (Mediabunny demuxers in Node, no ffprobe), `decide(info, caps, policy, audio)`, `keyframeIndex(read, size)` (Matroska cues, MP4 sample tables), segment plans, ffmpeg arguments, the Node remux producer, subtitle→VTT (SubRip/WebVTT files in Node, the rest through ffmpeg), `createMediaTools` (probe and keyframe caches, process limits, ffmpeg detection → `serverConversion()`), `createHlsSessions(options)` with on-demand segments, the session limit, HLS disk budget and fps/CPU sampling | An input URL or path, policy, the ffmpeg path | Tabs, routes, the app's port |
| `http-kit` | Router, Range parsing, conditional caching, `serveFile`, JSON helpers | Requests/responses | Core logic; only apps use it |
| `observability` | Structured logs, bounded Debug capture, metrics and runtime collectors | Logger/metrics options, lifecycle ownership | Domain operations and HTTP responses |
| `api-contract` | Types for the server JSON API (replaces `api-types.js`), the codec keys, the settings schema with `validate()` and the status level helpers, which run on both sides | — | Node or DOM APIs |

`@magplay/release` collects release notes and writes the application version, the versions of named packages, the root changelog and those packages' changelogs ([package readme](../packages/release/README.md)). The server and the client do not import it.

Each package throws its own typed errors (busy, timeout, not found, cancelled, invalid input). `apps/server` maps them to HTTP statuses in one place.

Torrent detail requests use `torrent-engine.info()` to describe a ready torrent or read its saved `meta.torrent` directly. A cached file list does not activate WebTorrent, occupy an initialization slot, or wait for cached-piece verification; file indices and content warnings use the same description logic as active torrents. Missing or invalid saved metadata falls back to the normal discovery path. Playback and downloads still use `get()`/`file()` and wait for torrent readiness before reading bytes.

### Apps

- **`apps/server`**
  - `config.ts`: all env parsing, including indexer configs, validated once. `loadConfig(env)` returns the settings store, `current()` (the configuration in use) and `onChange`.
  - `app.ts`: `createApp({ config })` creates the HLS sessions, media tools and torrent engine in that order, then the services and routes; `listen()`, `startupChecks()` and `close()`. Packages get live settings through `live()` options that read `config.current()`.
  - `main.ts`: the process: config, app, startup checks (sources, ffmpeg, Explore's counts), listening, and graceful shutdown on SIGTERM/SIGINT.
  - `services/`: play (probe → decide → direct URL, a browser-remux `/raw` URL, or an HLS session), tabs (one session per player tab, and fencing for closed tabs; "tab" is a browser concept), Explore (cache, parameter checks), search (rebuilt when sources change; recognizes magnets before contacting sources, using torrent-engine parsing to return one release without fetching metadata), torrents (adding by private link id), playlists, subtitles, and the status registry and checks.
  - `http/`: routes typed against `api-contract`, request parsing from `unknown`, the error→status mapping, static and built-client serving, `/raw`/`/tar`, `/hls` and the speed test.
- **`apps/client`**: one Vite-built HTML shell; `src/main.tsx` mounts React with TanStack Router (`src/router.tsx`) and one QueryClient (`src/lib/query.ts`). Search, Explore, Title, Torrent, Settings and the lazy Player route are TSX components. Router validates public URL/search parameters, preserves plain URLSearchParams encoding and restores scroll. In-app navigation uses Link; downloads, media, playlists and external applications use ordinary anchors. The Player's imperative `src/lib/playback-controller.ts` owns media and sessions; `Player.tsx` creates it in an effect and reads snapshots through `useSyncExternalStore`. Each infohash/file-index pair has a separately keyed controller lifetime. The client imports only API contracts and browser-safe dependencies; the stylesheet stays global. There is no vanilla-page bridge or per-page HTML/script lifecycle. React lazy/Suspense loads the Player; the route error boundary offers a full app reload if an old shell cannot fetch its lazy chunk after deployment.

The player's pure `lib/playback-status.ts` diagnoses the current wait; `lib/playback-flow.ts` presents it as four independently observed stages and an attributed wait location. It uses existing status and browser signals, exact selected-file completion, and published HLS readiness. `components/PlaybackFlow.tsx` preserves stage inspection, Diagnostics, focus and recovery menus across updates. `Player.tsx` owns the page-local pin; the controller retains a source-only snapshot for at most six seconds through session restarts; session and browser readiness do not survive those restarts. No new server endpoints or delivery-rate estimates support the flow. See [UI behavior](user-interface.md#playback-wait-explanations).

The torrent page is `apps/client/src/torrent.ts`, typed against the shared torrent/status contracts. It checks owned markup through `requireElement(selector, ctor)` and narrows browser history records before using them. Download-only primary actions use the existing `/raw?...download=1` or `/tar` routes; no eager torrent activation, new download job or second byte source is introduced.

### Upstream requests and secrets

- Indexer adapters fetch through `request()` in `packages/indexers/src/release.ts`. It follows redirects itself, only on the same server (an http → https upgrade included) and at most three times, so an `X-Api-Key` header or `apikey=` query never reaches another host. A redirect elsewhere is a `SourceError` asking for the new address. Bodies go through `readBytes`/`readText`/`readJson`, capped at 16 MiB by `Content-Length` and while streaming.
- Secret settings leave the server only as `{ set }`. [Logging and observability](logging.md) owns structured logging/redaction, metrics and collection architecture.

### `.local` source names

- mDNS multicast doesn't cross Docker's bridge network, so the container asks the host's avahi-daemon over its socket (`/run/avahi-daemon/socket`, mounted read-only from the host's `/run/avahi-daemon`).
- Resolution lives in the server (`apps/server/src/mdns.ts`), not in the image's libc. Alpine's musl has no NSS, so nss-mdns can't be used. A Debian base for `libnss-mdns` was tried and rejected: Debian's `ffmpeg` pulls in Mesa and LLVM, and the image grew from 457 MB to 987 MB.
- At startup, when the socket exists, `dns.lookup` is replaced by one that sends `.local` names to avahi (its `RESOLVE-HOSTNAME-IPV4/6` line protocol) and falls back to the original lookup for other names and failed answers. Node's `net`, and so `fetch`, reads `dns.lookup` on every connection; a unit test fetches through it so a Node change that breaks this shows up.
- ffmpeg only reads loopback `/raw` URLs, so it needs no mDNS. Resolution against a real avahi-daemon is still unverified (roadmap item 2).

### Settings and status

- **Schema.** `packages/api-contract/src/settings.ts` lists every setting once: key, section, scope (`server` or `browser`), control type, label, default and env vars. It holds only what a person tunes on the page; other knobs (ports, job limits, timeouts, trackers, ffmpeg paths) are env-only, resolved in `config.ts` (`envOnlyConfig`) with the same validation. Fields that accept an empty value are marked `optional`, shown on the page as "(optional)" by the label. The server validates env values, `settings.json` and `PATCH` bodies with the same `validate()` the client uses for `localStorage` and before saving. A new setting is one entry; the page, validation and API pick it up.
- **Settings presentation.** The schema declares presentation rules as a dependency key, an exact matching value, and overrides for visibility, disabled state, help or placeholder text. `apps/client/src/lib/setting-rules.ts` resolves them for both page settings and sibling fields in source items. Source guidance and URL examples follow the selected type, and Torznab omits the indexer filter. Hidden item fields retain their values across type changes. Conversion resolution follows the current draft toggle while preserving the chosen height; an environment lock always takes precedence. Source headings and Test button names follow URL edits in place using the hostname, without exposing URL credentials or replacing focused inputs. React controls in `lib/controls.tsx` keep inputs and disclosure elements mounted during edits and polling, preserving focus and expansion. Settings uses section components over the shared schema, a local draft and last-saved baseline, and Query mutations for Save, source Test and clearing conversions. Successful writes invalidate shared status/debug queries. Changes to source configuration or search timeouts also clear cached search/discovery results because the server rebuilds private download-link mappings; source, BitMagnet and adult-content changes clear affected Explore/title caches. Test results describe only the exact source values that were tested; a late response cannot label an edited endpoint. The debug query loads initial server capabilities and polls every five seconds while Storage or Debug is on screen; hidden tabs pause polling. Navigation or unloading with unsaved edits asks before discarding them.
- **Save confirmation.** A successful save records a four-second expiry deadline and schedules a refresh. New edits clear the confirmation and cancel its timer; a subsequent save replaces both. Rendering and page visibility/pageshow events check the deadline so delayed background timers cannot leave an expired confirmation visible. Browser tests advance a controlled clock for expiry, repeated saves and returning after a missed deadline.
- **Server resolution.** `apps/server/src/settings-store.ts` resolves env, then `<CACHE_DIR>/settings.json`, then the default, records where each value came from, and writes the file atomically (temp file and rename). An invalid env value stops startup naming the variable; an invalid saved value is ignored with a warning. `loadConfig()` in `config.ts` combines the env-only knobs with the page's settings into one typed `Config`, replaced on the store's `changed` event, so a saved setting applies on its next use (packages read limits and paths through their `live()` options, search and Explore are rebuilt).
- **Status registry.** `apps/server/src/services/status.ts` holds checks (`id`, `label`, `ttl`, `required`, `run`), runs stale ones when `/api/status` is asked (waiting up to 4 s, then reporting `unknown`), and turns a throw into `error`. `services/status-checks.ts` registers the checks: one per source, Explore, ffmpeg and disk. A missing ffmpeg is a `warn` (the core image's mode), never an `error`: the server runs without it. The shared status query merges browser checks (the connection test) and computes the overall level with the same `overallLevel()`. It polls every 30 seconds while visible, every second while required startup checks remain unknown, and refetches on opening the menu; there is no separate listener store or manual in-flight cache.
- **Writes** (`PATCH /api/settings`, `POST /api/settings/test`, `POST /api/debug/clear-hls`) require `Sec-Fetch-Site: same-origin` or a matching `Origin` (`isSameOrigin` in `http-kit`), since there is no login.
- **Browser preferences** live in `localStorage`, one JSON value per setting under `magplay:<key with : for .>` (`magplay:player:volume`), the same keys the Player's `recall()`/`remember()` use. Only volume and mute are in the schema (both `hidden`); the Player's other remembered choices — speed, audio and subtitle language — are its own keys, read raw with their own fallbacks, and have no Settings controls. `apps/client/src/lib/preferences.ts` exports the keys (`PREFERENCE`, `STORAGE_KEYS`) and parses values against the schema on read.

- **Where values live.** `settings.json` is in the folder `CACHE_DIR` names at startup (`./data` by default); the Cache folder setting moves torrent and HLS data, not the settings file, so startup never depends on a saved value to find its settings. Sources are items `{ id, type, url, apiKey, indexer }` (`indexer` is Jackett's indexer or filter, or Prowlarr's comma-separated ids; `apiKey` is optional — Jackett and Prowlarr need one, a plain Torznab feed usually doesn't); env items are locked and listed first. Secrets go out as `{ set }` and the browser sends `{ set: true }` back to keep one, matched by item id. Volume and mute are browser settings marked `hidden`: stored and validated, not shown on the page. GB settings are binary gigabytes (1024³).
- **Checks.** Every adapter has a cheap `check()` (Torznab `t=caps`, Prowlarr `/api/v1/health`, BitMagnet GraphQL `{ __typename }`). The status button's problem count includes warnings, so Explore without BitMagnet shows amber until its address is set.
- **Connection test.** Its controls and results are in the Debug section of Settings; connection status actions link to `/settings#debug`. `GET /api/speedtest` streams one reused 1 MB buffer of random bytes (defeating compressing proxies), honours backpressure, stops on `close` and caps at about 256 MB; it is `no-store` and counts against no session limit. `measureConnection()` in `apps/client/src/lib/speedtest.ts` takes the median of five `/health` fetches for latency, then reads one `/api/speedtest` response, skips the first ~1 s as warmup and stops at ~5 s. The result is stored per browser (`magplay:connection`) and feeds the `connection` client check: `warn` below 10 MB/s or above 100 ms, `unknown` if it never ran or is older than 7 days. It runs only on demand. The result card and status menu use the same warning helper to identify download speed below 10 MB/s, latency above 100 ms, or both; they do not infer a network cause.
- **Undecided:** whether env values should be importable into `settings.json`; whether a worsening level deserves a toast; whether the 30 s poll and 60 s source TTL suit rate-limited Prowlarr instances; whether the connection test should ever run unprompted; and the connection thresholds, pending real-server numbers (roadmap item 2).

### Rules

- Each workspace has its own `package.json` listing its dependencies and its own `tsconfig` with project references, so an undeclared import fails type checking. ESLint rejects imports of another package's internal files.
- Factories, not singletons: anything holding processes, timers, ports, sockets or directories is created by a factory and released by `close()`. No work at import time.
- Data from outside (indexer XML/JSON, BitMagnet GraphQL, request bodies, `localStorage`) is `unknown` until a small parse function returns a typed value.
- A split must reduce coupling. Moving a large file into an equally coupled package is not progress.

### HLS streaming

Remux and transcode play from one HLS playlist per player session that covers the whole file, on the file's own timeline, as direct play and browser remux do. The client never converts between a session time and a file time: `video.currentTime` is the position in the file, seeking is a normal seek, and subtitles and the seek bar use the same times. The server converts on demand. This replaced live-growing sessions that started at the keyframe before the request and restarted from an offset on every seek (2026-10-23).

- **Segment plan.** Copied video must be cut on keyframes, and every ffmpeg run must cut the same segments wherever it starts. `keyframeIndex()` reads keyframe times from the file's own index with a few range requests on `/raw` (Matroska `Cues` through the `SeekHead`, or the MP4 video track's `stss`/`stts`/`ctts`/`elst`), and `keyframePlan()` groups them into segments of at least 6 s. A cue list that misses keyframes only makes segments longer. Transcoded video uses `fixedPlan()`: every 6 s, with ffmpeg forcing a keyframe on each boundary.
- **Runs.** One producer at a time per session writes fragmented MP4 to fd 3 with a fragment at every keyframe: ffmpeg, or on a server without it a Node remux (`nodeRemuxProcess()`, Mediabunny) that behaves like an ffmpeg process (progress on stdout; SIGSTOP, SIGCONT and SIGKILL pause, resume and cancel it). The session splits the stream (`fragmentSplitter()`), reads when each fragment's first video sample is shown (its `tfdt` plus the sample's composition offset, which B-frames make positive), and publishes a planned segment once one run has covered it from its start to the next boundary. A segment request is answered from published segments, by waiting when the running ffmpeg will reach it within 30 s of media (one segment when transcoding), or by restarting ffmpeg there. ffmpeg pauses (SIGSTOP) 240 s ahead of the later of the player's position and the last segment asked for. Published segments stay until the HLS disk budget evicts the ones furthest from the player; only then are producers stopped.
- **Timestamps** (verified with ffmpeg 6.1; see [the checkpoint](checkpoints/2026-10-23-vod-playback.md)). A run that starts at file time `T` uses `-ss (T − start_time)` (left out when not positive, since `-ss` counts from the file's start time) and `-output_ts_offset (T + 10)`, so every run's media timestamps are the file's own plus 10 s. `-movflags +frag_keyframe+empty_moov+default_base_moof+frag_discont -use_editlist 0 -avoid_negative_ts disabled` keeps every start offset in `tfdt` and the init segment byte-identical across runs. hls.js never reads edit lists and Chrome's MSE ignores empty edits, so without `frag_discont` each run's `tfdt` starts at 0 with its real start only in an edit list (audio ran ahead of video that way). With the offset nothing is negative, so the muxer must not shift a track to make it so: `negative_cts_offsets`, or ffmpeg's default `avoid_negative_ts`, moved video by the B-frame delay against audio. Copied video keeps the container's timebase (`-copytb 1`): ffmpeg 6 otherwise derives the timescale from the codec and rounds an MKV's millisecond timestamps into it. The probe's start time (the earliest first timestamp of the tracks, from Mediabunny) can differ from ffmpeg's by the audio codec's priming delay, which shifts every fragment by the same few milliseconds; the session learns that skew from the first fragment against the nearest indexed keyframe and takes it off.
- **Restarts.** Copied video restarts one indexed keyframe before the boundary. A Node remux trims there and Mediabunny rebases its output to that keyframe, so the producer shifts every `tfdt` back by the keyframe's time (plus 10 s); ffmpeg seeks 0.15 s past it, because its CLI moves an input seek about 0.13 s earlier when the video has B-frames, with `-noaccurate_seek`. That warm-up output is dropped: the audio for a segment's first moments is stored before its keyframe, and starting exactly on the boundary left a 0.7 s audio hole. Transcoded video seeks exactly to the boundary. Where two runs' segments meet, video matches to the millisecond and audio overlaps by under one AAC frame.
- **Subtitles** from the same ffmpeg use `-output_ts_offset T`, so cues are on the file's timeline; `sub_N.vtt` returns every run's cues and the player skips ones it already has. A Node remux doesn't extract embedded subtitles.
- **Frame timing.** An open GOP's leading pictures and every other frame keep the source's presentation times, and a restarted run presents the same frames at the same times from its boundary on; `tests/e2e/hls-sync.test.ts` checks this and audio/video alignment (a flash and a tone) through the real arguments with edit lists ignored.
- **No index** (MPEG-TS, AVI, an MKV without cues, fragmented MP4) or no duration: one run from the start and a growing EVENT playlist (`growing` in the decision and status). The player can seek only as far as conversion has reached and jumps to a resume position once it gets there.
- If an index names a keyframe that isn't one, the segment is served from the fragment that covers its start (a small overlap the browser replaces) and `hls.plan.mismatch` is logged.

## Build and tooling

TypeScript uses `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `noFallthroughCasesInSwitch`, `noUnusedLocals` and `noUnusedParameters` through the shared base configuration. `noPropertyAccessFromIndexSignature` stays off: bracket-only access added noise to intentionally dynamic env, schema, dataset and upstream records without finding a defect in the tightening review. Browser application and colocated test projects remain separate so Node globals do not leak into browser code.

The lint baseline is `recommendedTypeChecked`, plus exhaustive switches, consistent type imports, `restrict-plus-operands`, `no-unnecessary-type-conversion` and `use-unknown-in-catch-callback-variable`. The full strict/stylistic presets were evaluated; rules that rewrite safe numeric interpolation, void callbacks, collection syntax or defensive runtime checks are not enabled globally. Reconsider individual rules when a concrete failure warrants them, rather than maintaining hundreds of suppressions.

Assertions require a nearby invariant or a documented boundary: bounded indices into nonempty collections, successful pattern captures, schema-validated values, owned static markup and deliberately partial test doubles. The sole production double cast bridges Node fetch's async-iterable body and this project's DOM declarations in `indexers/release.ts`. Vendor declarations stay minimal in the consuming package; no explicit `any` is used. Inline lint suppressions must name a rule and explain the reason; the router's `@ts-expect-error` is a deliberate negative type test. The [Phase 7 checkpoint](checkpoints/2026-10-19-typescript-review.md) records the audit and validation.

- **Server:** runs `.ts` directly with Node's built-in type stripping; no emit step. Only erasable TypeScript syntax is allowed (no `enum`, `namespace` or parameter properties).
- **Client:** Vite (`vite.config.js`, with the React plugin) builds the shell in `apps/client` into gitignored `dist/client/`, with its links rewritten to `[name]-[hash]` bundles and the stylesheet under `dist/client/assets/`, with sourcemaps. The server answers each page URL with the built shell, read on each request; other paths stay 404. The Player view is a lazy chunk; hls.js and the mediabunny codec chunks are loaded on demand only by playback that needs them. Shared runtime module preloads may appear in the shell, but Player/media chunks are not preloaded there. `npm run dev` runs Vite's dev server (hot reload) in front of the Node server, which it proxies for `/api`, media and playlists. `tsc` does type checking only.
- **Node baseline:** 24 LTS.
- **Container image:** the runtime stage is Alpine 3.24's `nodejs` package. `node:24-alpine` stays the build image only, because the runtime does not need the npm, yarn and headers it adds. The dependency stage keeps the current platform's native prebuild, strips its debug info, and drops other platforms, tests, TypeScript sources and duplicate published builds; Mediabunny accounts for most of that. `magplay` adds Alpine's `ffmpeg` package and no other ffmpeg. Client source maps stay, because the server serves them. Sizes are in [the image-size checkpoint](checkpoints/2026-10-19-docker-image-size.md). Cutting files out of `node_modules` changes the download, not the resident set in [container memory](resources.md#container-memory).
- **Linting:** ESLint (latest major, pinned, flat config) with typescript-eslint type-aware rules and neostandard for style. neostandard matches the existing code style (no semicolons, space before function parentheses), so no separate formatter is needed. Lint covers:
  - correctness the compiler misses, mainly floating or misused promises in the abort/lifecycle code and exhaustive `switch` over discriminated unions;
  - type hygiene: `import type`, no explicit `any`, `@ts-expect-error` only with a reason;
  - package boundaries: imports go through a package's public entry, never its internal files, and Node built-ins are banned in `apps/client`, `api-contract` and `release-info`.

  `npm run lint` runs in CI next to `typecheck`.

Requirements for the client build, kept from the earlier Vite criteria:

- Preserve `/`, `/explore`, `/title/…`, `/t/…` and `/play/…`, ordinary links and reload/Back behavior. The client router must keep every one of them working on reload and Back, and the server answers only the listed page routes. No SSR.
- Keep sources and generated output separate; build output goes only to gitignored `dist/`.
- Update Node serving, Docker packaging and smoke tests together, and test the production artifact (deep links, `hls.js` loading, playback), not only a dev setup.
- Revalidate HTML (`no-cache` with a content ETag). Only content-hashed `/assets/…` files are `immutable`, so reverse proxies and browsers pick up a release on the next page revalidation. Preserve media Range/cancellation policies and non-cacheable live responses/errors.

Vite remains an option if a dev server or bundled browser-media/WASM dependencies become a need; the requirements above apply to it too. No build system makes decoding or server remuxing faster by itself.

## Desktop distribution direction

Desktop packaging is a backburner item, not implemented or scheduled. Electron is the selected shell, with the existing interface in a dedicated BrowserWindow, bundled FFmpeg/ffprobe and target-specific native torrent dependencies. Electron main/preload code stays in TypeScript; the backend retains indexer, torrent, settings and media responsibilities in a supervised utility process using Electron's Node runtime. A separately bundled Node child is the fallback only if the packaged native-dependency spike requires it. Headless Node/Docker remains a separate launch mode of the shared backend.

The window loads pages, APIs and media from one loopback HTTP origin after readiness. The renderer has Node integration disabled, context isolation and sandboxing enabled, and only a narrow validated preload bridge. Electron is preferred over Tauri's system webviews and a browser-only launcher for a controlled Chromium playback runtime and an established Node desktop stack; actual codecs and native modules still require packaged tests on every target. Desktop resources resolve independently of the checkout, application data uses writable user directories, and persisted client preferences must survive a changed loopback port. [The desktop packaging plan](plans/desktop-packaging.md) owns the release matrix, Forge packaging, implementation phases, process containment and acceptance criteria; [the roadmap](roadmap.md#backburner) owns its deferred priority.

## Static delivery

A frontend proxy is not a cross-origin client. Nginx can serve the static pages and built client and proxy `/api`, `/raw`, `/tar`, `/hls`, `/subs` and playlists under the same origin. This needs neither CORS nor authentication. Node-only serving stays supported.

## Probe and playback modes

`probe` in `packages/playback/src/probe.ts` reads a file's headers with [Mediabunny](https://mediabunny.dev/)'s demuxers (MP4/QuickTime, Matroska/WebM, MPEG-TS and the audio containers) over a Range-reading `UrlSource` or a file path, in the Node process: container id (`mp4`, `mov`, `matroska`, `webm`, `mpegts`), duration, the primary video track (codec, profile and bit depth from the codec string, dimensions, sample aspect, frame rate), audio tracks (codec, channels, language, title, default) and, for Matroska, subtitle tracks from a small EBML scan of the `Tracks` element, which the demuxer does not expose. It also reports the file's start time (the earliest first timestamp of its tracks). Codec names stay ffmpeg-like (`h264`, `hevc`, `aac`, `ac3`, …) because `decide`, the capability keys and the labels key on them. There is no ffprobe anywhere.

`decide` picks one of four modes from the probe, the browser's capabilities and the policy's `serverConversion` (ffmpeg detected at startup and whenever `FFMPEG_PATH` or the encoder setting changes):

- `direct`: a faststart MP4/WebM the browser plays from `/raw` on its own.
- `remux` (ffmpeg): playable video codec, but the container or audio isn't; ffmpeg copies the video into an HLS session and converts the audio (see [HLS streaming](#hls-streaming)).
- `browser-remux` (no ffmpeg, and the page has Media Source Extensions): the same case, done in the page. The play request says so with `browserRemux`. `apps/client/src/lib/browser-remux.ts` reads `/raw` with Mediabunny, copies the video packets, converts the audio to AAC with WebCodecs (a WASM AAC encoder, and WASM AC-3/DTS decoders, loaded on demand), and feeds fragmented MP4 to a `SourceBuffer` whose `timestampOffset` is the keyframe the conversion starts on, so the timeline is the whole file and seeking or switching audio never asks the server for anything. Conversion stays one minute ahead of the playhead; buffered media more than 30 s behind is evicted; a seek outside the buffer restarts conversion from the keyframe before the target. The decision has no session and no server subtitles. Containers it handles are those the demuxers read; audio codecs are those the browser or the WASM decoders decode.
- Node remux (no ffmpeg, and the page has no Media Source Extensions): the same Mediabunny conversion runs in the server process as the producer of an ordinary `remux` HLS session (the same full-file playlist and on-demand segments), so the page plays it with hls.js or native HLS. The session's encoder is `node`. All three codec extensions (AAC, AC-3, DTS) are registered for the session, in worker threads. Embedded subtitles are not extracted; `.srt` and `.vtt` files still are. ffmpeg, when it is installed, still does every remux. The conversion's memory is anonymous buffers and those workers, not the V8 heap; a small container is sized in [resources](resources.md#container-memory).
- `transcode` (ffmpeg, opt-in): everything else that ffmpeg can re-encode.

Without ffmpeg, a file that would need a transcode, or embedded subtitles, is refused with a message that names the external player route; `.srt` and `.vtt` files in the torrent are converted to WebVTT in Node. The `core` Docker target (`magplay-core`) is this configuration; the `full` target (the `magplay` image, the default) is `core` plus Alpine's ffmpeg. Both run the same code: ffmpeg's absence is an operating mode, reported by the ffmpeg status check as a warning and by `/api/debug` as `serverConversion: false`, which the settings page uses to disable the transcode controls.

## Transcode encoder selection

Encoder detection first reads `ffmpeg -encoders`, then runs one bounded, one-frame lavfi encode for each listed hardware candidate. A hardware encoder is available only when that encode succeeds with the same VAAPI device path used by an HLS session; detection failures never prevent startup. libx264 needs no runtime probe and remains the floor for `auto` and unavailable explicit choices. Detection runs at startup and existing refresh points, not when each HLS session starts.

The published Alpine image's ffmpeg includes VAAPI and, on x86_64, Quick Sync support, but the image deliberately includes neither VAAPI driver libraries nor the Intel oneVPL GPU runtime. Its ffmpeg does not compile NVENC, and VideoToolbox does not exist on Linux. Consequently, the stock image selects libx264 unless a hardware probe succeeds. Passing `/dev/dri` into the container is necessary for VAAPI or Quick Sync but is not sufficient without the matching userspace driver; the image does not add GPU drivers, Mesa, Intel compute runtime, NVENC support or another ffmpeg build.

## Framework and browser-media triggers

The trigger for a framework, shared reactive state and component composition becoming the dominant maintenance problem, was reached in the Player and Settings. The client uses React with TanStack Router and Query, built by Vite. Server data lives in Query; URL state lives in Router; transient UI state lives in its owning component. No form/state framework or server rendering is added. The media controller stays imperative, a plain TypeScript class that React only renders. The player's lifecycle and abort ownership is described in [lifetime rules](lifecycle.md).

Browser remuxing exists for servers without ffmpeg (see [Probe and playback modes](#probe-and-playback-modes)); when ffmpeg is present the server still remuxes, because it works in every browser and costs the client nothing. Browsers can't reach ordinary TCP/UDP swarms, so browser torrenting still needs compatible peers or a bridge. Cross-origin hosting and general browser video transcoding are not current requirements.

## Invariants

- Node keeps indexer secrets, torrent discovery and cache, probing and server conversion. The browser client consumes API and media contracts.
- `/raw` is the single source of torrent bytes for the browser (direct play and browser remux), the probe, ffmpeg, downloads and external players; `/tar` shares its Range, validator and cancellation semantics. `playback` receives the `/raw` loopback URL as its input from the app.
- Wire contracts are TypeScript types in `api-contract`, backed by narrow runtime parsing at boundaries.
- Fast unit tests live next to the modules in each package. Cross-application tests live in `tests/integration/` and `tests/e2e/`. Docker and static artifacts exclude tests and fixtures.
- Run `npm run test:all` for meaningful media/lifecycle changes, and repeat the isolated Docker check (`tools/scripts/check-docker.mjs`) when packaging or runtime behavior changes.
- Commit coherent, verified steps; keep moves, type conversion and behavior fixes in separate commits.
